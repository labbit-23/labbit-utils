## 1. Orthanc was in a crash loop — root cause found and fixed

Not related to anything in this worker's own plumbing. Windows Service
`Orthanc` was terminating every 60-90 seconds (confirmed via
`Get-WinEvent` — 14 terminations logged since 2026-09-10 16:19). Orthanc's
own log pinpointed it exactly:

```
Starting Worklist Housekeeper worker thread
[+60s] Bad file format: Cannot parse an invalid DICOM file (size: 10 bytes)
```

The Worklist Housekeeper thread rescans `E:\OrthancWorklists` every 60
seconds and tries to parse every file there as DICOM. A corrupt 10-byte
file (`upload_1789048827979.wl`, written 2026-09-10 19:30:27) was crashing
the whole process on every scan cycle. Root cause of *that* file: the
bridge's own fallback-naming path (`mwl_bridge.py`, see below) writes
whatever bytes it decodes even if they're garbage — it was very likely an
earlier hand-built test POST with a malformed/tiny `mwl_dicom_base64`
value. Deleted the file, restarted the service, monitored 14+ minutes
clean (past both the 60s and ~90s points it had died at before) —
confirmed fixed.

A red herring along the way: `OrthancAwsS3Storage.dll` also appeared in
several crash dumps (access violation) and was disabled (renamed to
`OrthancAwsS3Storage.disabled`, matching the existing convention already
used for `OrthancGdcm.disabled` in the same folder) since the site owner
confirmed it's not used. Turned out not to be the actual cause — the
corrupt worklist file crashed the service again 92 seconds after S3 was
already disabled. Left S3 disabled anyway since it's genuinely unused, but
don't rely on that alone if this crash pattern ever recurs — check
`E:\OrthancWorklists` for another stray/corrupt file first.

test is a live "Query Worklist" from each console, not C-ECHO.

## 4. Sonology needs per-procedure station routing — added to the worker

Real workflow, confirmed by the site owner: two US machines, general
dopplers/sonology can be performed on **either** machine, but cardiology
dopplers always go to a fixed machine (`ESAOTE`). The worker's prior design
(one static `destination.aet` per instance, from the 2026-09-10 doc) can't
express "usually either, but sometimes exactly this one."

Added `mwl.station_overrides` to `radiology_mwl_worker.py`
(commit `38a2fd5`): a keyword-to-AET list checked against the resolved
`requested_procedure_description` (from the source's `procedure_name`),
case-insensitive substring match. A match pins `ScheduledStationAETitle`
to that override's AET; no match falls back to `destination.aet` (leave
that blank for sonology so either registered US machine's query can pick
it up). See the README's new "Splitting one department across multiple
machines by procedure type" section for the exact config shape.

## 5. The bridge endpoint and its auth — confirmed by direct test, not assumed

Read `E:\OrthancScripts\mwl_bridge.py` directly rather than trusting the
prior doc's memory of it. Confirmed:

```
mwl.create_url    = "http://100.84.172.71:8042/mwl-bridge/upload"
mwl.create_method = "POST"
mwl.transport     = "json_base64"   (unchanged from 2026-09-10 finding)
```

It's served through Orthanc's own HTTP server (port 8042) via
`orthanc.RegisterRestCallback`, not a separate service.

**New finding**: tested directly (sent `{}` — the handler rejects it
immediately with no field, so nothing gets written to disk regardless of
auth) —

```
no auth        -> HTTP 401
wrong creds    -> HTTP 401
radio:radio    -> HTTP 200, {"ok": false, "error": "... no mwl_dicom_base64 field"}
```

Orthanc's global HTTP Basic auth **does** apply to this custom Python
route, even though the callback code itself has no auth check — Orthanc
enforces it at the HTTP layer before the callback ever runs. So
`mwl.create_headers` in the worker config must include the Basic auth
header or every upload will fail with 401:

```json
"create_headers": { "Authorization": "Basic cmFkaW86cmFkaW8=" }
```

(`cmFkaW86cmFkaW8=` is `radio:radio` base64-encoded.)
