## 2. The bridge script — deployed, working, uses json_base64 not multipart

`E:\OrthancScripts\mwl_bridge.py` on the same Windows box, an
Orthanc-Python-plugin `RegisterRestCallback` at `POST /mwl-bridge/upload`.
Writes the received `.wl` file into `E:\OrthancWorklists` (the folder the
Worklists plugin watches).

**Important finding, not documented anywhere in Orthanc's own docs:**
Orthanc's Python plugin invokes a REST callback **once per multipart
field** for a `multipart/form-data` POST, not once for the whole request
— and something in that path breaks the real HTTP response no matter
which invocation answers (confirmed: file writes to disk successfully
every time, but the client always gets `Content-Length: 0` back). A
plain single-shot POST with a JSON body works perfectly. So: **the
worker's `mwl.transport` config must be `"json_base64"`, not
`"multipart_file"`**, when pointed at this bridge. Checked Orthanc's
official Python-plugin docs directly — they only document the simple
single-invocation case, so this isn't a misuse of a documented feature,
it's genuinely unspecified/broken territory that's easy to hit again if
anyone "fixes" this back to multipart later.

Bridge expects, matching the worker's own `json_base64` transport shape:
```json
{
  "accession_number": "...", "patient_id": "...", "patient_name": "...",
  "modality": "...", "mwl_file_name": "....wl", "mwl_dicom_base64": "<base64>"
}
```
Tested directly (not via the real worker, via a hand-built equivalent
payload) — confirmed `{"ok": true, "written": "...", "bytes": 574}` and
the file lands correctly in `E:\OrthancWorklists`.

Also has its own local log at `E:\OrthancScripts\mwl_bridge.log`
(everything wrapped in try/except so a bug in this script can never take
the whole Orthanc service down — it already did, twice, from copy/paste
syntax errors during this work, before that logging was added).

## 3. Source endpoint — do NOT use the labbit-py / Shivam path

The worker's README/example config points `source.poll_url` at
`https://api.sdrc.in/py/delivery/department-worklist` — this is
`labbit-py`, which internally calls a **legacy Shivam-era TApiQuery
endpoint**. Confirmed reachable and technically working, but this is the
wrong source: everything else in this integration fleet has been
deliberately migrated off Shivam onto Labit Core's `machine-api`, and
using Shivam here would be a step backwards (per direct instruction from
the site owner this session: "Shivam would be the wrong place").

**The correct source, already live and already returning real data:**
```
GET https://labit.sdrc.in/machine-api/mwl?department_name=radiology
Headers: X-Api-Key-Id / X-Api-Secret   (same credential pair already used
         for every other machine-api integration — provisioned in
         Mirth's configurationMap as LABIT_API_KEY_ID / LABIT_API_SECRET)
```
Confirmed live: **128 real pending radiology orders** returned today,
fields already exactly matching the worker's default `payload_fields`
mapping (`reqno`, `patient_id`, `patient_name`, `patient_sex` already
M/F/O, `patient_dob` already YYYYMMDD, `reqdt`/`reqtm`, `procedure_name`,
`modality` — already correctly resolved server-side, e.g. `"CR"` for a
chest X-ray — and `performed` as a real JSON boolean, not the example
config's string `"0"` sentinel, so `source.pending_value` needs to be
JSON `false` to match). Other departments confirmed resolvable too:
`ct_scan` → `DPT00050`, `sonology` → `DPT00038` (both returned 0 rows in
the window checked, confirmed by the site owner as a genuine data gap —
low/no imaging volume that week — not a department-mapping problem).

## 4. Real logic gap found, not yet fixed anywhere — needs a labit-core change

Worked through the push/cleanup logic with the site owner and caught an
important direction check: `.wl` files must be pushed while
`performed: false` (pending) — that's the entire point of MWL, the
scanner needs to see it *before* the exam — and **removed** once
`performed` flips to `true` (stale entry, exam already done). Not the
reverse.

But right now `machine-api/mwl?department_name=X` returns the entire
backlog of `performed: false` orders regardless of whether the patient
has physically arrived at radiology yet. There's no "patient presented /
checked in" timestamp anywhere on `Labit Radiology Order` — checked the
full field list (existing fields: `requisition, patient, patient_name,
patient_dob, patient_sex, modality, study_description, scheduled_at,
performing_unit, radiologist, mwl_pushed, mwl_pushed_at,
study_instance_uid, accession_uid, images_received, images_received_at,
image_count, report_status, report_attachment, report_text,
report_approved_at`) — genuinely nothing between "order scheduled" and
"images received."

**This needs a new field pair on `Labit Radiology Order`** (something
like `patient_presented` / `patient_presented_at`, same shape as the
existing `mwl_pushed`/`images_received` pairs) **plus a decision on who
sets it** — presumably radiology reception/check-in, but that workflow
doesn't exist yet either. Until this exists, `machine-api/mwl` would
need to keep returning the full pending backlog, which means pushing
worklist entries for patients who haven't shown up yet — not something
to wire the worker up against for real deployment without this fixed
first, even though the plumbing (source → transform → bridge → Orthanc)
is otherwise proven end-to-end.

This is genuinely a `labit-core` change (new doctype field + a UI/API
trigger point), not something fixable from the worker or Mirth side —
flagging it here specifically because whoever's working on labit-core
directly is best placed to add it.
